# Golang 项目代码审查提示词

请对以下 Golang 项目进行全面的代码审查，从以下方面进行检查：

## 1. 代码质量与风格
- 是否遵循 [Go Code Review Comments](https://github.com/golang/go/wiki/CodeReviewComments) 和 [Effective Go](https://go.dev/doc/effective_go) 规范
- 变量、函数、包命名是否清晰、符合 Go 命名约定
- 代码格式是否正确（是否通过 `gofmt` 检查）
- 注释是否充分，特别是导出的函数和类型
- 是否有冗余代码或复杂的嵌套逻辑

## 2. 错误处理
- 错误是否被正确处理而非忽略
- 是否避免使用 `panic` 进行常规错误处理
- 错误信息是否清晰有用
- 是否正确包装错误（使用 `fmt.Errorf` with `%w` 或 `errors.Wrap`）
- 是否正确处理 context 取消

## 3. 并发安全
- Goroutine 的使用是否合理，是否有泄漏风险
- Channel 的使用是否正确（是否有死锁风险）
- 共享变量是否需要加锁，锁的使用是否正确
- 是否正确使用 `sync.WaitGroup`、`sync.Mutex`、`sync.RWMutex` 等
- 是否避免数据竞争（可用 `go run -race` 检测）

## 4. 内存与性能
- 是否有不必要的内存分配
- 是否正确关闭资源（文件、数据库连接、HTTP 响应等）
- 是否正确使用 `defer` 进行资源清理
- 是否有内存泄漏风险（如 Goroutine 泄漏、未释放的缓存）
- 是否合理使用指针，避免过度使用
- 字符串拼接是否使用 `strings.Builder` 而非 `+` 在循环中

## 5. 安全问题
- 是否有 SQL 注入风险（是否使用参数化查询）
- 是否有 XSS、路径遍历等 Web 安全问题
- 敏感信息（密码、密钥、Token）是否硬编码
- 输入验证是否充分
- 是否正确处理 CSRF、CORS
- 依赖包是否存在已知漏洞

## 6. 数据库与 I/O
- SQL 查询是否高效，是否有 N+1 查询问题
- 是否正确使用数据库事务
- 数据库连接池配置是否合理
- 是否正确处理 I/O 超时
- 是否使用 context 设置超时

## 7. 架构与设计
- 代码组织是否清晰，包划分是否合理
- 接口设计是否合理，是否符合 Go 的接口惯例
- 依赖注入是否合理
- 是否有过度的耦合
- 是否遵循 SOLID 原则

## 8. 测试
- 是否有足够的单元测试
- 测试覆盖率如何
- 是否有表驱动测试
- 是否正确使用 mock
- 是否有集成测试或端到端测试

## 9. 依赖管理
- go.mod 依赖是否合理，是否有不必要的依赖
- 依赖版本是否过时
- 是否使用标准库而非重复造轮子

## 10. 配置与环境
- 配置是否通过环境变量或配置文件管理
- 敏感配置是否与代码分离
- 是否支持不同环境（开发、测试、生产）

## 11. 日志与监控
- 日志级别使用是否合理
- 是否记录关键操作和错误
- 是否结构化日志
- 是否有健康检查端点

## 12. Go 版本特性
- 是否充分利用当前 Go 版本的特性
- 是否有过时的用法

## 13. API 设计（Web 服务项目）
- RESTful 规范是否遵循（HTTP 方法、状态码使用）
- 请求/响应结构是否一致（统一的 Response 包装）
- API 版本化策略（如 `/api/v1/`）
- 是否有 Swagger/OpenAPI 文档
- 分页、排序、过滤参数是否规范

## 14. 优雅关闭（Graceful Shutdown）
- 服务是否能正确处理 SIGTERM/SIGINT 信号
- 是否等待正在处理的请求完成后再退出
- 数据库连接、缓存连接是否正确关闭
- 定时任务是否正确停止

## 15. 容器化与部署
- Dockerfile 是否使用多阶段构建减小镜像体积
- 是否使用非 root 用户运行
- 镜像体积是否合理（推荐使用 alpine 或 distroless）
- 健康检查配置是否正确
- 是否支持环境变量注入配置

## 16. Clean Architecture 检查（适用于分层架构项目）
- 层级依赖是否正确（内层不依赖外层）
- Entity 是否保持纯净（无业务框架依赖）
- Repository 接口与实现是否解耦
- Usecase 是否只依赖接口而非具体实现
- Delivery 层是否只负责协议转换，不包含业务逻辑

---

## 输出要求

请按照以上标准对项目进行审查，并给出：

1. **发现的问题**（按严重程度分类：严重/中等/轻微）
2. **每个问题的具体位置和代码示例**
3. **改进建议**
4. **优先级排序**

---

## 使用说明

将此提示词配合 AI 工具使用时，可以：
- 根据项目类型（Web 服务、CLI 工具、库等）调整审查重点
- 添加项目特定的业务规则或约束
- 指定特定的文件或包进行审查
